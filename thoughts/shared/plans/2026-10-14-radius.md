## Problem in domain terms

pi-messages sends pi's own transcript (`TranscriptContext.messages`, system messages included) to `<baseUrl>/messages` and gets pi's
assistant-message events back. The invariant: what the gateway receives is the transcript byte for byte (no `transformMessages`, no
per-API rewrite), and what the session stores is what the gateway said (usage with its server cost, responseId, providerThinkingLevel).
Levels the fix lives at: backend (new `llm_be_pi_messages`), neutral event/accum (server-owned usage and ids), registry (catalog
replaced as a whole), app glue (cache file, refresh points). The root is the backend plus the registry; nothing is patched in the UI.

Searched before writing: `llm/be_*.c` (nearest: be_openai_codex.c for head/path, be_anthropic_pi.c for pi messages), `llm/accum.c`,
`llm/models_json.c` (add models), `login.c pi_auth_io/pi_auth_provider_token` (HTTP + token), `authstore.c` (atomic file write).
Nothing for a gateway catalog or models-store.json exists.

## Exemptions (written, owner may veto)

- R10: the failure diagnostic embeds `error.stack` (JS frames); no consumer in amiga-pi (pi's bug-report upload is not ported). The error text itself (R9) is exact. Stored sessions from a failed request therefore lack `diagnostics`.
- Toolcall extra fields other than `id`, `name`, `arguments`, `thoughtSignature` in `toolcall_end.toolCall` are not carried (the message model has no slot).
- A server `error` event with `reason:"aborted"` ends as an error stop (the retry gate in llm/retry.c reports LS_ERROR); pi would store `aborted`. A server error event without `errorMessage` stores the text `error`.
- A 200 answer whose Content-Type is not `text/event-stream` is reported as an HTTP failure (llm_post), pi reads any body.
- `debug` option (`?debug=1`): the coding agent never sets it (checked in coding-agent/src/core and agent/src); the SDK-only knob is not exposed.
